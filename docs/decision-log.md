# 판단 기록

면접에서 "왜 이렇게 했나"를 설명하기 위한 기록이다. 날짜는 모두 2026-10-25.

## 1. 문제 선택

- KT IS 114는 2025년 4월부터 상담원이 카카오 T 택시를 대신 불러주는 서비스를 운영한다 (전자신문 2026-08-07, 누적 약 15만 건·6만 명).
- 한 건마다 **듣기 → 되묻기 → 앱 입력 → 결과 읽기**를 반복한다. 반복이 크고 순서가 정해져 있어 AX 효과를 재기 좋다.
- 대상이 어르신이라 잘못 호출되면 피해가 크다. 효과와 안전장치를 같이 설계해야 하는 문제다.

## 2. 처음 계획 → 바꾼 계획

| | 처음 | 바꾼 뒤 |
|---|---|---|
| 목표 | AI가 전화를 받고 혼자 호출 | 상담원의 반복 업무를 얼마나 줄이나 검증 |
| 사람 역할 | 없음 (예외만 넘김) | AI 제안을 확인·수정하고 호출 승인 |
| 음성 | STT·TTS가 핵심 | STT는 받아쓰기 보조, TTS는 핵심에서 제외 |
| 비용 계산 | 상담원 인건비 대체 | 처리시간·재작업 감소 vs AI 운영비 |

바꾼 이유: 직접 써 보니 음성 인식이 안 됐고, 합성 목소리는 기계적이었고, 기능이 커져서 설명하기 어려웠다. 완전 자동은 지우지 않고 비교용으로 남겼다.

## 3. 기술 선택

| 기술 | 고른 이유 | 버린 대안과 이유 |
|---|---|---|
| 규칙 기반 장소 정리 | 왜 그렇게 정리했는지 근거(몇 번째 말, 어떤 조사)를 보여줄 수 있다 | LLM: 자유 발화엔 강하지만 근거 설명·비용·키 관리 부담. 다음 단계 후보 |
| Playwright 화면 자동화 | 배차 플랫폼 API는 제휴가 필요하다. 상담원이 쓰는 화면을 대신 조작하는 게 현실적인 첫 단계. 같은 도구로 E2E 테스트 | 공식 API: 가장 안정적이지만 제휴 전에는 불가 |
| Vercel Functions + 서버 Chromium | 공개 데모에서 실제 브라우저 조작을 보여줄 수 있다 | 녹화만 보여주기: 실시간이 아니라 설득력이 약함 |
| Web Speech API | 서버 키·비용이 없다 | 상용 STT·TTS: 품질은 높지만 비용·키. → 결국 이 선택이 가장 큰 실패 원인 |

## 4. 실패와 판단

1. **음성 인식이 안 된다.** 진단 화면으로 나눠 보니: 내장 창은 권한 차단, 자동화 Chrome은 말소리 감지 후 결과 없음, Edge는 인식 서버 연결 오류. 사람이 직접 말해 성공한 기록 없음.
   → STT를 핵심에서 빼고 받아쓰기 보조로 낮춤. 실패해도 상담원이 입력하면 흐름이 이어지게 함.
2. **목소리가 기계적이다.** 이 PC에서 쓸 수 있는 한국어 목소리는 기기 합성음 하나.
   → 품질을 주장하지 않음. 보조 방식에서는 상담원이 직접 말함.
3. **장소 정리가 자신 있게 틀린다.** 1차 34건 중 26건 정답. 규칙을 고친 뒤 같은 34건은 32건(과대평가 가능), 처음 보는 16건은 13건. 남은 오류는 '동대문시장 → DDP'처럼 키워드가 겹쳐서 생김.
   → AI는 제안만 하고 상담원 확인을 필수로 함. 완전 자동은 이 오류가 없는 통화 유형을 찾은 뒤에 검토.
4. **동시 실행 제한이 안 걸린다.** 2건을 동시에 보내자 둘 다 실행됨. 제한이 서버리스 인스턴스마다 걸리기 때문.
   → 상용화하려면 Worker 앞에 전체 대기열이 필요하다고 기록.
5. **시간 절감은 재지 못했다.** 잰 것은 조작 수(수동 13~18회 → 보조 4~5회)뿐. 사람이 아끼는 초는 사람 없이 잴 수 없다.
   → 비용 계산의 '건당 40초 절감'은 가정으로 표시하고, 파일럿에서 가장 먼저 잴 값으로 정함.

## 5. 다음 단계 제안

- 상담원 몇 명과 2주 파일럿: 건당 처리시간, 입력 오류율, AI 제안 확인에 드는 시간 측정
- 실제 녹취(동의 받은 것)로 장소 정리 정확도 재측정
- 손익분기(건당 약 14초 절감, 기본 가정 기준)를 넘는지 확인한 뒤 확대 여부 결정
